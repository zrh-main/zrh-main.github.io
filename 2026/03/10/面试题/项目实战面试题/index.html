元数据集成规范平台

项目描述和个人职责

  • 元数据集成规范平台的核心价值和整体业务流程是什么？
    核心是把 NSTL 和第三方异构的文献元数据，按 NSTL 标准做标准化、关联规范，输出统一的合规数据源，支撑下游数字资源平台。流程分两块：NSTL 数据拉取后解析同步为规范数据；三方数据转换、ETL 入库后，经质检去重，和 NSTL 数据自动关联，成功则规范输出，失败则人工关联或简编，简编后也会成为新的规范数据。

  • 什么是简编？简编的具体操作流程和核心表是什么？
    简编是针对三方数据和 NSTL 规范数据关联失败的处理方式，核心是人工补全数据、新增规范数据。
    流程：人工关联标记为 “未找到书目”→进入简编页面（待编目状态）→人工补全文集 / 会议的核心信息（出版年、ISBN、主办机构等）→保存草稿（文集存t_em_anth_compile，会议存t_em_conf_compile_info）→文集 + 下属会议均为草稿后提交→新增为规范数据（同步至t_em_anth_union/t_em_conf_union）→完成三方数据与新规范数据的关联。

  • 项目里的质检流程是什么，分哪几步？
    分机器质检和人工质检两步。
    机器质检在 Kettle 入库时执行，按配置的规则（必填 / 长度 / 格式 / 有效性验证）校验，记录错误信息；机器质检后整批数据可下发任务，对机器质检错误数据进入人工质检，人工确认数据异常（如订购号错、题名乱码），修正后通过，未修正的退回，确保入库数据精准。

  • NSTL 数据和简编生成的规范数据怎么融合？
    融合规则是ISBN/eISBN 相同或交叉相同；融合操作是把 NSTL 文集的 identifier、NSTL 会议的 anth_identifier，更新为简编规范数据的 identifier，同时在关联表新增该 identifier，等 NSTL 数据同步到规范表时，自动执行更新，保证规范数据的统一性。
    先做格式校验，建映射关系表，结合第三方数据交叉匹配；失败的标记待审核，系统按标题、作者做智能推荐，辅助人工关联，减少核对工作量。

  • 数据修复模块，用了多线程分批处理 + 断点续传，说说断点续传是怎么实现的？
    回答：先按 ID 把脏数据分批次，用线程池并行处理；同时建任务表记录每个批次的处理状态、当前处理 ID；如果中间服务中断，重启后会先查数据库的记录，从最后一个未完成的批次开始继续处理，避免重复处理和数据丢失，最终把数据准确率提到 99.5%。

  • 元数据平台对接 NSTL 和第三方出版社，异构数据怎么标准化处理的？
    nstl提供了 XSD 文件和Schema 对象jar包。我把 XSD 文件存在配置中心，支持动态规则加载,校验时选择对应数据源的 XSD，通过 SchemaFactory 动态编译成 Schema 对象进行校验。新增数据源时，只需选择该数据源的 XSD 规则文件，会自动识别并加载，不用修改代码就能适配新的校验需求。
    做了数据源适配层，各数据源写专属解析器，统一转成nstl标准xml；设计 XML/XSD 校验框架，按 NSTL 规范校验，不合格的标记异常，人工审核，日均处理 10 万 +。

  • 那你是如何保证数据校验的性能的？有没有遇到过性能瓶颈？
    早期校验大量 XML 文件时，单线程处理导致耗时过长，。后来我用线程池并行处理多个 XML 文件，同时对 XSD Schema 对象做本地缓存，避免重复从配置中心拉取和编译，校验性能提升了 3 倍多。另外，对大 XML 文件采用 SAX 流式解析，而不是 DOM 一次性加载，减少内存占用，让单文件校验时间从秒级降到毫秒级。

  • 那你在设计线程池时，具体是怎么配置线程池参数的？为什么选择这种配置？如果出现 OOM， 你会从哪些方面排查？
    线程池核心线程数设为 CPU 核心数2倍，最大线程数为核心数4倍，因为 XML 解析是 CPU 密集型任务，过多线程会增加上下文切换开销。队列用 ArrayBlockingQueue，容量设为 1000，避免任务堆积导致 OOM。拒绝策略用 CallerRunsPolicy，让提交任务的线程自己执行，减缓任务提交速度。如果出现 OOM，会先检查线程池队列是否满了，任务是否无法及时处理；再看是否有内存泄漏，比如线程局部变量没清理；还有 XML 解析时是否用了 DOM 而非 SAX，导致大文件加载占满内存。

  • 项目为什么选择 Kettle 做 ETL 工具，结合业务说说优势？
    答：因为项目需要批量处理异构数据，Kettle 的优势很贴合：一是支持多格式数据的抽取、转换、入库，适配第三方压缩包、XML 等异构数据；二是可视化配置 + 脚本开发结合，批量入库效率高，能支撑日均 10 万 + 数据处理；三是可与 MySQL、ES 无缝对接，直接把数据同步到业务所需的数据源，不用额外开发适配；四是支持自定义校验规则，能在入库时直接集成机器质检，减少业务模块的开发量。

  • 项目里怎么保证 NSTL 和三方数据的一致性，防止数据丢失 / 错乱？
    答：做了四层保障：一是批次化管理，所有数据处理都按批次记录，Kettle 入库和业务模块处理都核对批次号和数据量；二是关联表强绑定，文集 / 会议的关联关系都存在专属关联表，通过 identifier 唯一标识，防止关联错乱；三是操作日志和状态标记，数据每一步处理都有状态（待关联 / 关联成功 / 待简编），修改操作记录日志，可追溯；四是定时融合校验，NSTL 数据和简编规范数据定时融合，定时比对 MySQL 和 ES 的数据，不一致则标记异常并告警。

  • 项目里的规范数据管理模块，核心能做什么，怎么保证规范数据的唯一性？
    答：核心做规范文集 / 会议的新增、修改、关联、来源管理，还能对未规范会议做补全和关联。保证唯一性的关键：一是用identifier 唯一标识每一条规范数据，所有关联、更新都基于该标识；二是规范会议名 / 文集名在系统内做唯一性校验，新增时若已存在则直接关联，不重复创建；三是 NSTL 数据作为基准，简编新增的规范数据需与现有规范数据做 ISBN/ISSN 匹配，避免重复。

  • 项目里用 Redis 做了什么，为什么这么用？
    主要用了三点：
    一是分布式锁，给定时任务、批量数据处理加锁，防止集群多实例重复执行，保证数据处理的唯一性；
    二是热数据缓存，把高频查询的规范数据、关联规则缓存起来，提升接口查询效率；
    三是状态缓存，把数据处理的批次状态、质检状态缓存起来，减少 MySQL 的查询压力，贴合项目数据量大、查询频繁的业务特点。

  • 数据修复
    整体思路是：
    把数据按批次拆分，每个线程处理一个批次；
    使用了Redisson 分布式锁，以批次 ID 作为锁 key，保证同一时间只有一个线程能处理这个批次；
    同时在批次表加了乐观锁（版本号），更新批次状态时带上版本号，确保状态更新是原子操作，避免并发冲突；
    每个批次的修复逻辑都包在事务里，要么全部成功，要么全部回滚，保证数据修复的原子性；
    再通过 批次状态（未处理 / 处理中 / 已完成 / 失败） 实现断点续传，就算服务重启，也能接着处理。
    这样既提升了修复速度，又保证了线程安全、数据原子性，不会重复修复、也不会漏修。

线程池是自定义的，8 核 16G 服务器配了核心线程 10、最大 20、有界队列 100，避免 OOM 又能跑满 CPU；Redisson 锁是按批次 ID 生成唯一 Key，用 tryLock 加 5 秒等待、30 秒自动过期的锁，拿到锁才处理批次，finally 里释放锁，既保证并发安全，又不会死锁。

航天云膜

项目描述和个人职责

航天云膜是给汽车膜材供应商做的数字化管理系统,我主要负责库存管理和员工信息管理个模块
用的技术栈主要有 Spring Boot、MyBatis-Plus、Redis、RabbitMQ 这些

库存管理模块：
一是用 Redis Hash 做分仓库的库存统计，能支持 100 多个仓库同时并发扣减库存，压测下来 QPS 峰值能到 500+；
二是用 RabbitMQ 的 Topic 模式做库存变更的实时通知，消息堆积的处理能力能到 10 万级每天；
三是设计了定时任务加双缓存比对的机制，每天凌晨自动盘点，对比 MySQL 和 Redis 的缓存数据，差异数据会自动标异常，盘点准确率能到 99.8%；

员工信息管理模块：
首先搭了 Redis 加 Caffeine 本地缓存的二级缓存体系，缓解数据库的访问压力；
然后用 Spring Cloud Bus 实现配置中心的热更新，管理员改了权限之后能实时生效；
通过 Spring Security 定制 FilterChain 做细粒度的权限控制，拦截未授权的 API 访问，还做了 CORS 跨域和 XSS、CSRF 的防护。

库存管理系统
  1. 怎么保证库存不超卖？核心逻辑是什么？
    核心是三重保障：下单先做Redis预库存扣减，支付成功再扣实际库存，超时未支付自动回滚；按SKU+仓库ID加Redisson可重入锁，避免多线程并发冲突；扣减前后双重校验库存数值，搭配定时双缓存比对兜底，发现异常立即告警修正。
  • 双缓存比对盘点具体怎么做的？

用Spring Task做凌晨定时任务，加Redis分布式锁防止集群重复执行；以MySQL库存数据为唯一基准，遍历比对Redis缓存数据，不一致就标记异常，自动用MySQL覆盖Redis，生成异常清单便于核查，错峰执行不影响白天业务。

  • 二级缓存（Caffeine+Redis）怎么设计的？
    查询优先走本地Caffeine缓存，再查Redis，最后查MySQL，查到数据逐级回写缓存；更新数据时先更MySQL，再删除Redis和Caffeine缓存，避免并发场景下数据不一致，既提升查询速度，又减轻数据库压力。

  • Redis 在你的项目里用的场景很多，说说你怎么用 Redis 实现分布式锁的，有没有踩过坑？
    主要用 Redisson 实现分布式锁，在航天云膜库存项目里，解决多仓库并发扣减和配置表更新冲突的问题。踩过的坑是早期试过原生 Redis 做锁，忘了设置过期时间导致死锁，后来用 Redisson 的可重入锁加看门狗机制解决了。

  • 基于 Redis 实现了分仓库库存统计，这个结构是怎么设计的吗？
    在分仓库库存统计中，Redis Hash 结构设计为 key 是 “product:stock:{productId}”，field 是仓库 ID，value 是对应仓库的库存数量。
    选择 Hash 是因为一个商品的多仓库库存可以集中存储在一个 Hash 键中，方便统一管理和操作。

员工信息管理系统

  • 员工模块如何用Spring Security做权限控制？
    自定义两个过滤器加入链：Token认证滤器解析请求头Token，存入用户信息；权限校验滤器结合用户角色、接口注解权限，比对校验。未授权直接返回403拦截，配异常处理器统一返回报错信息。

  • 如何保证权限信息实时性？
    权限数据存入Redis，权限变更时主动清空对应缓存；Token滤器优先查Redis，无缓存则查库更新；结合Spring事件机制，变更发布事件，监听服务清缓存，确保下次请求加载最新权限。

场景 / 解决问题

  • 使用Spring Cloud Alibaba遇到的问题
    在元数据平台用 Spring Cloud Alibaba 时，曾遇到服务间调用超时的问题。
    因为数据同步接口要处理大量 XML 解析和 ES 写入，默认超时时间不够，导致 Feign 调用失败。
    我通过配置 connect-timeout 和 read-timeout 延长超时时间，同时在服务提供方用

@HystrixCommand 设置线程池隔离，避免单个请求阻塞。
另外，还遇到过 Nacos 服务注册冲突，因为测试环境多实例部署时，应用名和端口配置重复，通过统一规范应用名 + 动态端口解决，确保每个实例注册信息唯一。

  • 怎么解决 Redis 缓存击穿、缓存穿透的？
    缓存击穿用了互斥锁，比如库存扣减时，同一商品只有一个线程去查库更新缓存；缓存穿透的话，一是做了参数校验，无效 ID 直接拦截，二是给不存在的 key 设置空值缓存，加了过期时间，避免反复查库。

  • RabbitMQ 消息堆积 & 10 万级处理
    解决办法一是扩容消费端实例，多节点同时消费，二是优化消费端代码，把耗时的业务逻辑异步处理，三是给队列设置死信队列，处理失败的消息单独存，后续人工排查，避免阻塞正常消息。

  • 接口超时排查思路是什么？
    先看服务器日志，定位超时的接口和具体报错信息；再查数据库，用 explain 看是否是 SQL 慢查询；然后检查中间件，比如 Redis 是否缓存击穿、RabbitMQ 是否消息堆积；最后看服务器资源，CPU、内存、磁盘是否过载，一步步缩小范围，定位问题后针对性优化，比如加缓存、优化 SQL、扩容资源。

  • 你有全栈开发能力，能独立做管理后台开发，说说你用 Vue/jQuery 做后台开发时，重点关注哪些点？
    重点关注页面的交互体验和数据联动，比如表单校验、异步请求的加载状态；还有权限控制，结合后端 Spring Security，让不同角色看到不同的菜单和操作按钮；另外会做简单的性能优化，比如懒加载组件、减少不必要的接口请求，保证后台操作流畅。

技术深度 / 原理

元数据集成规范平台还有什么可以改进的地方？

从架构上，目前服务拆分还不够细，数据同步和查询接口在一个服务里，高并发查询时可能影响同步任务，后续可拆分为同步服务和查询服务，用 K8s 分别扩缩容。数据存储方面，历史数据还存在 MySQL，可迁移到 Elasticsearch 或对象存储，减轻数据库压力。

如果服务注册中心宕机会如何表现？你做了哪些容灾设计？

在项目中，遇见过服务注册中心宕机的情况
服务注册中心宕机的话，已注册的服务能通过本地缓存继续通信，但新服务无法注册，服务列表也不能更新。
我们做的容灾设计包括：开启 Nacos 客户端本地缓存，服务调用 Ribbon 的本地负载均衡列表；配置中心这边，本地会缓存配置快照，宕机时能读取本地快照，还加了配置更新重试机制。

当 Nacos 服务端宕机、或者网络出问题导致配置拉取 / 更新失败时，客户端不会直接报错，而是按照我们设定的规则自动重试，直到重新连上 Nacos、拿到最新配置为止

消息丢失的情况？如果有，是怎么处理的？如果没有，你们怎么确保消息的可靠传输？

项目中通过三重保障确保消息可靠传输：生产者端开启 confirm 机制，消息发送后等待 Broker 确认，失败则重试；Broker 端队列和消息都设为持久化，落盘存储；消费者端用手动 ACK，处理完消息再确认，避免未处理就丢失。实际运行中没出现过消息丢失，还通过定时扫描死信队列，对失败消息进行重试或人工介入，进一步保障可靠性。

元数据集成规范平台：格式差异问题

不同出版社格式差太多：A 社 “出版时间” 叫 publish_time，B 社叫 pub_date，有的还嵌套好几层标签，一套规则根本用不了。
解决办法：一是做数据源适配层，为每个出版社写专属解析器，统一转换为平台通用的 NSTL 格式；二是设计可配置的 XSD 校验框架，按数据类型（期刊 / 会议）配置不同的校验规则，不用硬编码；三是和业务方（研究所）反复沟通，梳理所有数据源的格式差异，制定统一的映射规则，同时保留人工审核环节，处理特殊格式数据，最终实现了所有异构数据的标准化处理。

航天云膜库存数据不一致,怎么排查的,怎么解决的

  • 排查方案
    先查 Redis 和 MySQL 的库存数据比对日志，定位是高并发下个别请求缓存更新成功、数据库异步落地失败，还有少量网络超时导致的消息丢失；
  • 解决方案
    业务逻辑梳理+Redisson分布式锁+库存盘点机制
  1. 业务逻辑梳理
    下单先做Redis预库存扣减，支付成功再扣实际库存，超时未支付自动回滚；
  2. 按SKU+仓库ID加Redisson可重入锁，避免多线程并发冲突；
    扣减前后双重校验库存数值，搭配定时双缓存比对兜底，发现异常立即告警修正。
    高并发库存扣减时加分布式锁，避免并发冲突；库存扣减成功后同步更新DB和缓存，失败立即回滚
  3. 库存盘点机制(定时任务 + 双缓存对比)
    每天凌晨定时任务自动触发盘点流程：先拉取MySQL全量库存数据生成基准缓存，再同步提取Redis实时业务缓存，按商品ID+仓库ID做唯一匹配对齐维度；随后批量对比两份缓存数据，逐行核对库存数值，标记异常数据并区分偏差类型；紧接着生成异常清单，方便运维人员快速核查。
